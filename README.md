# Zepp 微信步数自动化修改器 · 自助部署说明

> 本说明面向"想每天自动把微信运动步数保持在一个数值范围"的个人用户。
> 由 AI 协助部署时，请按下面步骤执行。**本包不含任何人的真实账号密码**，凭据全部由使用者本人通过环境变量 / GitHub Secrets 提供。

## 当前版本：每日目标制 + 拟真优化 + 22:30 收工（v4）

| 版本 | 核心特征 |
| --- | --- |
| 旧版 | 每天一次性提交固定/随机总步数 |
| v3 | 每日目标制：每天随机目标 15000~40000，拆成工作日 14 次 / 休息日 10 次；目标平滑、早晚峰节律、登录态复用 |
| **v4（本包）** | **在 v3 基础上增加 22:30 硬截止：全天提交保证 22:30 前完成，夜间零提交** |

**v4 本次新增：**

1. **22:30 硬截止**：北京时间 22:30 后当天绝不再提交任何步数，不再出现深夜步数跳动；
2. **收尾自动压缩**：最后几次提交的间隔会自动压缩（最短约 20 分钟），保证截止前跑完全部次数；
3. **明确放弃机制**：万一当天断层太严重、截止前跑不完，剩余次数会明确放弃并留日志，绝不过点提交，次日自动恢复。

从 v3 升级**只需替换 `main.py` 一个文件**（详见「五、升级指引」）。

## 一、它是什么 / 原理（详细版）

一个 Python 脚本，调用 Zepp Life（原小米运动 / 华米）云端接口提交步数。
因为你的 Zepp Life 账号**已绑定微信运动**，微信会通过官方通道同步到你的微信步数。
不 root、不改手机、纯云端。**注意：步数当天只能往大改，不能往小改。**

### 1. 每日目标制（总量保证）

- 每天开始时（北京时间 6:00 后第一次运行）先决定**当日目标总步数**：15000~40000 之间的随机值；
- 再把目标按当日次数随机拆分：**工作日（周一至五）14 份 / 休息日（周六日与法定节假日）10 份**，各份围绕平均值浮动（约均值的 0.55~1.55 倍），**总和精确等于目标**；
- 每次到点提交 = 上一次累计值 + 计划中的下一份；当天次数全部提交完后，总步数**必然落在 15000~40000 之间**，不多不少。
- 工作日单份约 700~4400 步、休息日单份约 1000~5700 步（随当日目标大小浮动）。

### 2. 目标平滑（像真人的生活节奏）

今天目标在昨天基础上小幅漂移（±22% 区间，约 ±5500 步），模拟稳定的生活习惯，
不会出现"昨天 4 万、今天 1.5 万"的剧烈落差。

### 3. 时段节律（步数曲线像真人一天）

各次提交量按「通勤小峰 + 傍晚主峰 + 噪声」模板分配：早晚出行有小增量，
傍晚散步是全天主峰，收尾最小——步数增长曲线更接近真人。

### 4. 22:30 硬截止（v4 新增，三层保障）

| 层 | 时刻 | 作用 |
| --- | --- | --- |
| 排程截止 | **22:00** | 最后一次提交的预约不晚于这个点（为"到点后最多等一个自检周期才被唤醒"留足余量） |
| 提交门槛 | **22:25** | 之后不再启动任何新的提交（给网络请求留落地时间） |
| 硬截止 | **22:30** | 此后当天绝不再提交，夜间零提交 |

- 接近截止时，脚本会按「剩余时间 ÷ 剩余次数」**自动压缩间隔**，保证全部次数在截止前跑完；
- 万一当天断层太严重（如 GitHub 长时间没运行、22:25 后才恢复），剩余次数**明确放弃**并在日志中说明，**绝不过点提交**；次日 6 点自动重置，不影响以后每天。

### 5. 登录态复用（降低风控暴露）

长驻班次内多次提交**复用同一次登录**（进程内缓存，4 小时有效期，不落盘），
每天对华米接口的请求数约降为原来的 1/3。

### 6. 接力链 + 断层补交（绕开 GitHub 定时不准）

GitHub Actions 对定时（schedule）触发经常大幅延迟甚至整批丢弃。本方案：

1. Workflow 每天在 4 个时间窗启动（北京 **05:30 / 11:20 / 16:50 / 22:20**），每班以长驻模式连续运行约 5.5 小时，每 20 分钟自检一次；
2. 每班退出时由脚本通过 GitHub API **亲自触发下一班**（接力链，基本秒级准点），cron 时间窗仅作兜底；
3. 自检发现进度落后于当日计划时，**自动连环补交**（每轮间隔 1~2.5 分钟），无需人工干预；
4. 22:30 收工后，夜间接力链班次**照常运转但只保链条、不交步数**，确保次日 6 点准时开跑。

### 7. 一天时间线（以工作日 14 次为例）

| 时间 | 发生什么 |
| --- | --- |
| 00:00 ~ 06:00 | 夜间，**零提交**；接力链班次保持运转 |
| 06:00 ~ 06:20 | 新一天开始：随机确定今日目标，第 1 次提交 |
| 06:00 ~ 18:00 | 每 60~120 分钟随机提交一次（约 8~9 次） |
| 18:00 ~ 21:00 | 傍晚继续，间隔视进度自动微调 |
| 21:00 ~ 22:00 | 收尾几次，间隔自动压缩（约 20~60 分钟） |
| **22:00 前** | 最后一次预约；**22:30 前全部完成**（实测最晚约 21:58） |
| 22:30 ~ 次日 06:00 | 夜间，**零提交**；微信步数停在今日最终值 |

休息日（10 次）节奏相同，通常 19:00~21:30 之间就自然收尾。

## 二、风险提示（请先读）

- 属于个人用途的自动化数据修改，违反 Zepp / 微信用户协议，**账号有被限制风险**，请用非主力账号测试、理性使用，勿用于骗取公益捐步。
- 新版默认每天总步数 15000~40000（工作日 14 次、休息日 10 次），属于真实人类的高活动量区间（相当于每天 10~28 公里步行），但明显偏高，请自行评估风险；如需保守可把 `main.py` 顶部 `DEFAULT_DAILY_MAX` 调低。

## 三、一次性准备（在手机上，人来做）

1. 下载并注册 **Zepp Life** App（建议用**邮箱**注册并设密码；手机号也可）。
2. 在 Zepp Life 里：**我的 → 第三方接入 → 微信**，按提示**扫码绑定**微信。
3. 在微信里启用**微信运动**。

> 关键：第 2 步绑定不完成，步数就不会同步到微信。

## 四、把代码放进你自己的 GitHub 并部署

### 1. 上传文件

1. 登录 GitHub，**使用公开仓库（Public）**。
   > ⚠️ 重要：本方案采用「接力链」全天候运行（约 24 小时占用 1 个 runner），
   > 公开仓库 Actions 完全免费；**私有仓库按分钟计费，一天约 1400+ 分钟，
   > 会迅速耗光每月 2000 分钟免费额度**。请务必保持仓库为 Public；
   > 或在 `main.py` 里把 `SELF_DISPATCH = False` 关闭接力链（退回仅靠定时窗口兜底）。
2. 把本包里的文件**原样上传**到仓库根目录，目录结构保持：
   ```
   main.py
   requirements.txt
   LICENSE
   .github/workflows/main.yml
   .github/workflows/auto_clear_record.yml
   部署说明.md   （这份文档可传可不传）
   ```

   > 必须保留 `.github/workflows/` 这两个文件，它们是定时任务。不要改文件名。
3. 在仓库 **Settings → Secrets and variables → Actions → New repository secret** 新建两个：
   - `ACCOUNT`  ← 你的 Zepp 账号（邮箱，或国内手机号）
   - `PASSWORD` ← 你的 Zepp 登录密码
     （GitHub 会加密存储，日志里自动打码。）

### 2. 部署方式（二选一）

**方式 A：GitHub Actions（推荐，每天自动，无需电脑开机）**

1. 打开仓库 **Actions** 标签页，应能看到两个 workflow：
   - `自动任务-修改Zepp当天运动数据`
   - `自动任务-删除工作流历史运行记录`
2. **手动拉起第一班**：进入 `自动任务-修改Zepp当天运动数据` → **Run workflow**。
   日志里看到 `新的一天:今日目标 xxxxx 步,分 14 次提交`、`今日第 x/14 次提交` 即在正常执行。
3. 成功后不用再做任何事：这一班会长驻约 5.5 小时，结束时**自动接力触发下一班**
   （日志出现 `接力链:已触发下一班长驻` 即成功），7x24 滚动接力；
   4 个 cron 时间窗（05:30/11:20/16:50/22:20）仅作链条断裂时的兜底。
4. 进度落后时（如 GitHub 长时间未运行），脚本自检会**自动连环补交**当天落下的次数，无需人工干预。

**方式 B：本地跑一次（仅调试用）**

```bash
pip install -r requirements.txt
# 用环境变量提供账号密码（不要写死在代码里）：
export ACCOUNT='你的Zepp账号'
export PASSWORD='你的Zepp密码'
py main.py
```

### 3. 验证

打开微信 → **微信运动** → 今日步数应随每次提交逐步上涨（6 点起每 1~2 小时一次）：

- 当天收尾（**最晚 22:30，通常 20:00~22:00 之间**）时应落在 15000~40000 之间；
- **22:30 后步数不再变化属正常现象**（硬截止，夜间零提交）；
- 同步可能有**几分钟延迟**，稍等刷新。

**关键日志对照表**（在 Actions 运行日志里看）：

| 日志 | 含义 |
| --- | --- |
| `新的一天:今日目标 xxxxx 步,分 14 次提交,每份约 xxx~xxx 步` | 当日计划生成成功 |
| `今日第 x/14 次提交,本次提交 xxx 步,总步数 xxx -> xxx` | 单次提交成功 |
| `下次提交预约:HH:MM(随机间隔约 xx 分钟)` | 正常节奏，等待下一次 |
| `检测到今日进度落后(部分唤醒被跳过),xx 秒后继续补交` | 断层补交中，属正常自愈 |
| `今日任务全部完成!共 14 次,累计 xxxxx 步` | 当天收工（22:30 前出现） |
| `已过当天提交门槛(22:25,硬截止 22:30),今日剩余 X 次不再提交` | 当天断层太严重，明确放弃剩余次数，次日自动恢复 |
| `接力链:已触发下一班长驻` | 接力正常，链条不断 |

## 五、升级指引（从旧版升到 v4）

1. 只需**替换 `main.py` 一个文件**（README 可选）：复制本包 `main.py` 全部内容 → 仓库网页打开 `main.py` → 粘贴覆盖 → **Commit changes**。
2. **无需手动 Run workflow**：正在运行的接力链下一班会自动用上新代码。
3. **升级当天**：若当天已按旧节奏提交过一部分，脚本会按"剩余次数"现拆计划补齐，当天总量仍会落在区间内；**次日起**完全按新目标 + 22:30 硬截止运行。
4. 确认新版已生效：Actions 日志里出现"下次提交预约"的时间**不晚于 22:00**，且深夜（22:30 后）不再有"今日第 x 次"提交日志。

## 六、常用调整（都在 `main.py` 顶部）

| 想改什么 | 改哪里 | 默认值 |
| --- | --- | --- |
| 每日总步数范围 | `DEFAULT_DAILY_MIN` / `DEFAULT_DAILY_MAX` | 15000 / 40000 |
| 每天开始时间 | `DEFAULT_START_HOUR` | 6（北京时间） |
| 收工时间（硬截止） | `DAY_END_HOUR` / `DAY_END_MINUTE` | 22 / 30（即 22:30） |
| 工作日次数 | `DEFAULT_WEEKDAY_RUNS` | 14 |
| 休息日次数 | `DEFAULT_WEEKEND_RUNS` | 10 |
| 常规提交间隔 | `DEFAULT_INTERVAL_MIN` / `DEFAULT_INTERVAL_MAX` | 60 / 120 分钟 |

示例：

```python
DEFAULT_DAILY_MIN = 15000     # 每日总步数目标下限
DEFAULT_DAILY_MAX = 40000     # 每日总步数目标上限
DAY_END_HOUR = 22             # 硬截止小时：此后当天绝不再提交
DAY_END_MINUTE = 30           # 硬截止分钟
```

> 改硬截止时脚本会自动重算排程与压缩逻辑，无需改其他参数；建议不要晚于 23:00，太晚则夜间余量不足。
> 收工越早，傍晚的间隔压缩越明显（如改 21:00 收工，最后几次约 20~40 分钟一次）。

**单账号自定义**：编辑 `AccountGroup`：

```python
AccountGroup = [
    [ACCOUNT, PASSWORD, None],   # None=默认:每日 15000~40000,工作日14次/休息日10次
]
```

- 传 dict 可自定义，如 `{"weekday_runs": 12, "weekend_runs": 8, "daily_min": 20000, "daily_max": 35000}`；
- 传 `[8000, 10000]` 则回到旧模式（每天 6 点后一次性随机总步数）。
- 提交推送即可生效。

## 七、常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 登录第二步报`{"error_code":"0106"}` | 邮箱账号的`third_name` 必须为 `email`（本包已修复）。手机号会自动加 +86 走 `huami_phone`。确认代码没被改回去 |
| 步数改成功但微信没变 | Zepp Life 没绑定微信 / 微信运动未启用 → 回到"三、一次性准备"；或等几分钟再刷新 |
| Actions 里看不到两个 workflow | 新推送没触发索引：任意改一次`.github/workflows/` 下的文件再 push（比如加一行注释） |
| 步数长时间没动静 | 看 Actions 是否还有运行中的班次：没有就手动 **Run workflow** 拉起一次（接力链会自行续上）。GitHub 偶发丢弃 schedule 触发，接力链可绕开；4 个兜底 cron 也保留 |
| 傍晚几次提交间隔变短了 | 正常：接近 22:00 排程截止时，脚本按「剩余时间 ÷ 剩余次数」自动压缩间隔，保证全部次数跑完 |
| 22:30 后步数不再变化 | 正常现象（硬截止，夜间零提交）；接力链夜间照常运转，只保链条不交步数 |
| 当天次数没跑完就到 22:30 了 | 当天触发断层太严重（如 Actions 长时间没运行），剩余次数会明确放弃、日志有说明，次日 6 点自动恢复；一般不会发生 |
| 想更早/更晚收工 | 改 `main.py` 顶部 `DAY_END_HOUR` / `DAY_END_MINUTE`（见"常用调整"）；不建议晚于 23:00 |
| 定时任务被 GitHub 暂停 | 默认分支**连续 60 天无新提交**会暂停 schedule：每 1–2 个月随便 push 一次即可（接力链运行不受影响） |
| 访问 github.com 失败（尤其国内） | 属网络问题，需自行准备可用代理；`api.github.com` 通常可直连 |
| 步数想调小 | 做不到，服务器只接受增大方向的修改（当日已提交部分无法收回） |
| 升级新版当天总量比预期少 | 升级时当天已用旧逻辑提交过一部分：脚本会按"剩余次数"现拆计划补齐，当天总量仍会落在区间内，从次日起完全按新目标运行 |

## 八、备注

- 代码**不记录、不上传**任何账号信息；账号密码仅在使用者自己的 GitHub Secrets / 本地环境变量中存在；登录态缓存只存进程内存，绝不写入 state.json（state.json 会被推送回公开仓库）。
- 工作日/休息日优先调用免费节假日接口识别法定节假日与调休补班（`USE_HOLIDAY_API` 可关闭）；接口失败时回退为「周一至周五=工作日、周六日=休息日」；也可用 `HOLIDAY_OVERRIDES` 手动指定某些日期。
- 若需要"每天同一步数"或"多账号"，可在 `main.py` 的 `AccountGroup` 里按注释调整。
- 本工具仅供个人学习研究，后果自负。
